# Decision log (ADRs)

Format: id | date | status. Never delete; supersede.

## ADR-001: PostgreSQL, serializable commit  — 2026-11-07 — Accepted
- **Context:** Slide 7 names PostgreSQL for versions, tokens and the audit chain. The commit must be atomic against races.
- **Options:** PostgreSQL; SQLite; Redis + app locks.
- **Decision:** PostgreSQL. Commit runs in one SERIALIZABLE transaction with row locks (`SELECT ... FOR UPDATE`).
- **Consequences:** UNIQUE constraints enforce G2 in the database, not app code. Serialization failures are retried or DENIED (fail closed).

## ADR-002: Dual extraction = pdfplumber + rasterize/OCR  — 2026-11-07 — Accepted
- **Context:** Slide 7: "pdfplumber plus a vision pass". The vision pass must stay out of the LLM trust path.
- **Options:** LLM vision model; Tesseract OCR on the rasterized box; second text library.
- **Decision:** Vision pass = PyMuPDF rasterizes the cited box, Tesseract OCRs it. Deterministic, no LLM, reads image-only values pdfplumber cannot. Both must agree or the claim fails.
- **Consequences:** Needs the Tesseract binary (`TESSERACT_CMD`). OCR error rate is a false-block risk, measured in Phase 6.

## ADR-003: Fixtures generated with PyMuPDF  — 2026-11-07 — Accepted

- **Decision:** `fixtures/make.py` writes PDFs with PyMuPDF and records exact bboxes, JSON pointers and sha256 in `manifest.json`.
- **Consequences:** Ground truth is exact; real-world scan noise is out of scope (slide 10 "Verifier-bound").

## ADR-006: Cumulative limits inside the commit transaction  — 2026-11-07 — Accepted
- **Context:** Two concurrent $4,900 approvals must not both pass a $5,000 cap.
- **Decision:** AP-CUM-03 is re-evaluated INSIDE the SERIALIZABLE commit transaction against locked cumulative rows, not only at prepare.
- **Consequences:** Prepare-time AP-CUM-03 is advisory; commit-time is authoritative.

## ADR-010: The tool executes inside the commit transaction; idempotency key at the tool  — 2026-11-07 — Accepted
- **Context:** Deck S2.4 "execution gap": retries, stale records and check-then-commit races. The gate must call the tool at most once per receipt and never on a DENY, and the system of record must not drift from what was approved.
- **Options:** (a) call `tool.execute` inside the SERIALIZABLE commit tx after every check; (b) commit a reservation, then call the tool outside the tx; (c) transactional outbox / two-phase with the tool.
- **Decision:** (a). `gate.commit` takes `LOCK TABLE commits IN SHARE ROW EXCLUSIVE MODE` as its first statement (before the snapshot is taken), so gate commits form one lane, the cumulative re-check sees every earlier commit, and SSI never aborts a commit after the tool ran. Inside the tx: consume review token, insert `commits` (UNIQUE nonce + idempotency key), cumulative re-check, `FOR UPDATE` version + diff hash (diff hash binds the dry-run diff AND the record's before-state), then `execute(req, version, idempotency_key, conn)` exactly once, a post-check that the tool moved the version by at most one, and the gate sets `version = receipt.version + 1`. Serialization failures (40001/40P01) are retried up to 3 times only while the tool has NOT been reached. Once the tool was reached, any failure rolls back and **burns** the receipt: a separate tx inserts the `commits` row (`ON CONFLICT DO NOTHING`), so a client retry is AP-REP-05 and the amount counts toward the cap (unknown outcome = spent, fail closed).
- **Consequences:** A crash after `execute` but before COMMIT can leave a tool-side effect with no `commits` row; the tool-side idempotency key bounds that. A hostile tool can still double-apply on its own side (mock `double_call`); the gate detects the extra version bump, rolls back and burns, but cannot undo a real external payment. One commit lane caps throughput. `# ponytail: global lock; upgrade path is a per (actor, vendor) lock row, then an outbox/two-phase tool protocol.`

## ADR-011: variance = invoice − PO; the policy uses abs  — 2026-11-07 — Accepted
- **Context:** Slide 2: invoice $4,800, PO $4,300, "unexplained $500". The sign of the difference must not let an over- or under-billing slip past AP-INV-04.
- **Decision:** `variance` is a DERIVED claim `sub(invoice.total, po.total)` (positive = invoice above PO). Rego compares `abs(variance)` in integer cents against 100.00. The gate also requires `amount`, `invoice.total` and `po.total` claims to equal the system-of-record values (invoice record total, PO total) — a document the agent supplies proves only what the document says.
- **Consequences:** Under-billing by more than 100.00 is also REVIEW. A self-made document cannot lower the variance or the amount below what the records say (AP-VER-01, G1).

## ADR-012: Identity comes from the transport, not the request  — 2026-11-07 — Accepted
- **Context:** Red team (Phase 3) proved `actor` and `on_behalf_of` were free strings written by the untrusted agent: an alias (`Agent-7`, `agent-7 `, a zero-width suffix, `agent-8`) reset the AP-CUM-03 actor+vendor cap, and naming a richer principal (`cfo`) borrowed its scope.
- **Options:** (a) trust the request; (b) bind the request to a caller identity the transport authenticated; (c) look identity up from an API key inside the gate.
- **Decision:** (b). `Gate.prepare(req, docs, *, principal)` and `Gate.commit(receipt, req, review_token=None, *, principal)` take a `Principal(actor, on_behalf_of)` (frozen dataclass in `gate.py`) established by the MCP session / adapter (Phase 5). It is REQUIRED with no default (a missing principal is a TypeError, never a fail-open), and `req.actor` / `req.on_behalf_of` must equal it exactly, else DENY `AP-SCOPE-02` / G1 "identity not bound to caller" (at prepare, and at commit after the hash check). `contracts.py` restricts both ids to `^[a-z0-9][a-z0-9_.-]{0,63}$`, so case, whitespace and zero-width aliases are contract errors. The cap key stays actor+vendor (deck S6).
- **Consequences:** The gate trusts the transport for authentication; a transport that maps every caller to one Principal would merge their caps (fail closed, not open). Tests use `tests/gatekit.KitGate`, which defaults to the honest test session `Principal("agent-7", "user-123")`; the production Gate has no default.

## ADR-013: variance is pinned to sub(invoice.total, po.total)  — 2026-11-07 — Accepted
- **Context:** Red team proved `verify.derived` recomputed whatever `fn`/`inputs` the agent named: `sub(invoice.total, note)` with an ASSERTED `note`, self-subtraction, `amount - invoice.total`, `po - po`, and a DIRECT variance from a self-made `calc.json` all produced 0.00 and turned a REVIEW into ALLOW.
- **Decision:** `verify.REGISTRY["payments.approve_invoice"]["pinned"] = {"variance": ("sub", ["invoice.total", "po.total"])}`: variance must be DERIVED with exactly that fn and those inputs (a DIRECT variance is rejected, ADR-011). A DERIVED input may only be a DIRECT or DERIVED claim that verified, or a system-of-record value; an ASSERTED claim, even "ok", is never an input. The gate also requires the variance value to equal `sor invoice.total - sor po.total` (Decimal, 2dp) at prepare and again at commit.
- **Consequences:** Only one variance can reach the policy: the records' own. A tool needing other derived fields must register its own pin.

## ADR-014: commit re-derives the policy from fresh state; burned receipts quarantine the record  — 2026-11-07 — Accepted
- **Context:** Red team proved commit re-checked only the invoice record and the cap: a delegation revoked or a vendor removed from scope after prepare, or a PO total changed (true variance now 500.00), still executed. And a burned (unknown-outcome) commit left the invoice `open`, so a fresh prepare with a NEW idempotency key applied it again (double effect).
- **Decision:** (1) Inside the commit tx, after the version/diff check and under the commit lock, the gate rebuilds the policy input from CURRENT state (delegation scope, PO total/vendor via `tool.sor_for`, committed sum excluding this row; amount and variance must still equal the records) and calls `policy.decide` again. Fresh DENY = DENY with OPA's rule ids (G1). Fresh REVIEW on an ALLOW receipt = DENY `AP-STALE-07` / G2. (2) `_burn` also inserts `quarantine(record_id, nonce, created_at)`. `prepare` DENYs `AP-REP-05` / G2 "unknown outcome from a previous attempt; reconcile" while a record is quarantined, and commit re-checks it inside the tx. `Gate.release_quarantine(record_id, reviewer)` is the admin reconcile path. The burn row and the quarantine row are written in separate transactions so one failing does not skip the other; a failure is reported as an extra AP-ERR-11 reason on the DENY.
- **Consequences:** One more OPA round trip per commit, inside the commit lane (latency, not safety). A record stays blocked until a human reconciles it with the tool's real outcome. `# ponytail: if both burn writes fail, a retry is bounded only by the tool-side idempotency key; release_quarantine gets an audit hook in Phase 5.` `mint_review_token` and `release_quarantine` are Gate methods for the human/admin side only; no tool-facing path (MCP, adapter) may expose them (ADR-008 still open).

## ADR-015: `commits.vendor_id` holds the counterparty id (documented reuse, no rename)  — 2026-11-07 — Accepted
- **Context:** ADR-009 keys refund AP-CUM-03 on (actor, customer) and asked to generalize `commits.vendor_id` to `counterparty_id` so one query serves both tools. The column is read and written by the gate (prepare sum, commit insert, commit cap sum, burn insert), by the demo seed, and by tests that insert or select it directly (`test_db.py`, `test_prepare.py`, `test_commit.py`, `tests/redteam/test_rt_g1_authority.py`).
- **Options:** (a) `ALTER TABLE commits RENAME COLUMN vendor_id TO counterparty_id` behind a guarded `DO` block, plus every reader/writer and test edited in the same change; (b) add `counterparty_id` and backfill, keeping both (two sources of truth for the cap key); (c) keep the physical column and document that it holds the counterparty.
- **Decision:** (c), the least change. `commits.vendor_id` is the **counterparty id taken from the system-of-record record**: the invoice's `vendor_id` for `payments.approve_invoice`, the payment's `customer_id` for `payments.refund_payment` (gate `TARGETS[tool].counterparty`, never a request field). `record_id` (`invoice:` / `payment:`) says which tool wrote the row. `schema.sql` carries a column comment; `commits_record (record_id)` is added for the refundable-balance sum (ADR-009).
- **Consequences:** No migration, no change to existing readers, every existing test (incl. the red team) runs unmodified. The cap key is `(actor, counterparty id)` across both tools, so a vendor id equal to a customer id would share one 5000.00 cap: stricter, never looser (ids are `V-*` and `CUST-*` today). The name is misleading to a new reader; the comment and this ADR are the mitigation. `# ponytail: name says vendor; upgrade path is option (a) in one migration once the console backend reads commits.`

## ADR-008: Reviewer separation of duties by directory person (AP-SEP-12)  — 2026-11-07 — Accepted
- **Context:** A REVIEW decision is executable only with a one-use human token (AP-REV-10). `mint_review_token(request_hash, submitter, reviewer)` took both identities as caller strings and only stored them. One person, or one compromised account, could submit and approve, which undoes the REVIEW control. LLM council, Phase 4 (`the council verdict summarised in this ADR`): all five advisors chose four-eyes. Peer reviewers and the coordinator added that it must compare verified *people*, not logins: one human with two reviewer logins, and admin role escalation.
- **Options:** (A) the reviewer must differ from actor and on_behalf_of, enforced in the gate, DENY with a rule id; (B) any reviewer-role holder, audited; (C) configurable per tool/threshold.
- **Decision:** (A), as `AP-SEP-12` / **G2** ("reviewer is the same person as the submitter (separation of duties)"). New directory table `people(login PK, person_id, roles[])`, covering console logins, on_behalf_of ids and agent ids (each agent mapped to its operator). The reviewer person is `people[console_session.subject]`, from the server-side session and never from a request. The submitter persons are `people[Principal.actor]` and `people[Principal.on_behalf_of]`, using the transport Principal (ADR-012). DENY if the reviewer person is among them, or if any lookup is missing (fail closed). An on_behalf_of that names a team without a single person also DENYs. Enforced twice:
  1. At mint. The new signature is `mint_review_token(receipt, req, *, reviewer_login)`: the gate verifies the receipt signature, the hash and `decision == REVIEW`, and reads the submitter from `req`. It requires the `reviewer` role (`admin` cannot mint) and stores `minted_by` + `minted_by_person`.
  2. Inside the commit tx, right after the token is consumed, by re-reading `people` under the commit lock. A violation rolls back.

  Seeded accounts: `rev-alice`, `rev-bob` (reviewers), `sub-user123`, `admin-ops`, and test-only `rev-user123` (same person as user-123).
- **Consequences:** A solo operator uses a second seeded reviewer, so there is no weaker default. (B) was rejected because it is the status quo the product exists to fix. (C) was rejected because a threshold exemption invites split-the-invoice. An audited, time-boxed, two-person break-glass is an explicit non-goal for the prototype. Collusion between two different people and reviewer session hijack are residual risks (THREAT_MODEL). Separation is only as strong as the console's authentication and the `people` data, so admin edits to `people` are audited, and the commit-time re-check catches edits made after a mint. `# ponytail: team on_behalf_of is DENY; upgrade path is a team_members expansion.`

## ADR-009: Second connector = refund (`payments.refund_payment`)  — 2026-11-07 — Accepted
- **Context:** A second connector goes end to end through the same gate. It must show taint AND cumulative limits in a 3-minute demo without diluting the INV-2048 hero. LLM council, Phase 4 (`the council verdict summarised in this ADR`): all five advisors chose refund, and every peer reviewer ranked the Executor's one-flow plan strongest. The coordinator's point decides it: with mock services, a bank-detail change has no system-of-record equality path (its taint check reduces to DIRECT verification alone), while a refund compares against a real original-payment record.
- **Options:** (A) vendor bank-detail change; (B) refund against an original payment with a per actor+customer cap.
- **Decision:** (B). Authority fields:
  - `payment_id`: DIRECT, and must exist in the system of record.
  - `customer_id`: equals the system-of-record payment's customer.
  - `refund_to`: equals the system-of-record payment's `method_id`. Documents can never fill it; taint is AP-VER-01 / G1.
  - `amount`: DIRECT at the cited box, and `<= payment.amount − committed refunds on that payment`, re-checked at commit (ADR-014).

  `reason` is not an authority field. AP-CUM-03 is keyed on `(Principal.actor, customer_id from the system of record)`, cap 5000.00, authoritative inside the commit tx (ADR-006/010). `commits.vendor_id` is generalized to `counterparty_id`. Demo:
  - `scripts/demo_seed.py --reset` seeds `PAY-7731` (CUST-311, 450.00, `pm_card_4242`) and prior refund commits of 4800.00 for (agent-7, CUST-311).
  - Fixture `REF-311.pdf` asks for 250.00 and carries an injected line redirecting the refund to a new account, which gives DENY AP-VER-01 (taint on `refund_to`).
  - The clean retry gives DENY AP-CUM-03 (4800 + 250 > 5000).

  The demo uses pre-generated, manifest-backed fixtures, not live extraction of unseen documents. Verification still runs.
- **As built (Phase 5):** `verify.REGISTRY["payments.refund_payment"]` marks `payment_id` and `amount` `direct_only` and `refund_to` `sor_only` (an untainted ASSERTED value equal to the payment's `method_id`; DIRECT or any `taint` is refused, so a doc-tainted copy that *equals* the record is refused too). `customer_id` follows the deck taint rule (DIRECT, or ASSERTED confirmed by the record) and the gate requires it to equal the payment record. Refunds above 1000.00 are REVIEW `AP-REF-13` / G1 (SEP-12 applies unchanged). The refund customer scope is `delegations.customers`. The counterparty column is ADR-015.
- **Consequences:** The beat order is fixed: hero REVIEW, injected DENY, replay DENY, concurrent $4,900 (one DENY), then refund (about 40 s at most). If the taint refusal cannot land in one frame, the refund segment is cut from the video, never the hero. The refund destination redirect carries the BEC story that bank change would have told. A per-actor key lets one human running several agents spread refunds across actors. `# ponytail: per-actor cap key; upgrade path is a people.person_id key.`

## ADR-016: AP-CUM-03 also caps per person behind on_behalf_of  — 2026-11-07 — Accepted
- **Context:** The cap was keyed on (transport actor, counterparty). agent-7 spent 4900.00 on V-BRK for user-123, then agent-8 (another agent, same human p-user123 in `people`) spent another 4900.00: both executed (`atk-spl-actor-rotation`). ADR-009 recorded this as a ponytail.
- **Options:** (a) replace the actor key with a person key; (b) keep the actor key and add a person key; (c) key on the actor's operator person.
- **Decision:** (b). The deck names "cumulative limits per actor and vendor", so the actor cap stays. A second cap, same 5000.00 and same rule id AP-CUM-03 (G1), keys on (person behind `on_behalf_of`, SoR counterparty). Person = `people.person_id` of the Principal's on_behalf_of login; an unmapped on_behalf_of is its own key (never a free pass). Policy input gains a required `cumulative.person_committed` (2dp string): Rego `well_formed` requires it, so a caller that omits it DENYs AP-VER-01 (fail closed; `Gate._policy_input` omits it when not given). Inside the commit tx, under the existing commit lock, the gate checks the actor sum, then the person sum (this row included), then passes both (minus this row) to the ADR-014 fresh decision. When both trip, one reason is returned (the actor one). No new column: the sum joins `commits.on_behalf_of` to `people` at decision time (least change; no backfill, test inserts stay valid).
- **Consequences:** Rotating actors, or switching between two on_behalf_of logins of one person, no longer resets the cap (`tests/redteam/test_rt_g1_rotation.py`, incl. a 10-round race). One extra indexed-by-vendor sum per prepare and per commit. A directory remap re-keys past commits (admin, audited). `tests/attacks/test_refund_cap.py::test_cap_is_per_actor_and_other_agents_do_not_count` encoded the gap; it now asserts another agent for ANOTHER person does not count and another agent for the SAME person does. `# ponytail: person key read through the directory at decision time; upgrade path is a person_key column stamped at commit if directory history must not re-key.`

## ADR-017: one money-config OCR re-read before a Disagreement (ADR-002 follow-up)  — 2026-11-07 — Accepted
- **Context:** Tesseract (`--psm 7`, 300 dpi) misread the benign total `$4,419.49`, so the dual-extraction check failed closed on a correct document (a false block). The benign corpus had been edited to 4420.00 (`BENIGN2_OCR_FIX`), which hid the false block from the measured rate.
- **Options:** (a) keep the corpus edit; (b) loosen `agree` (fuzzy match); (c) one re-read of the same box with a money-oriented config, exact agreement still required.
- **Decision:** (c). In `extract_pdf`, if the text layer and OCR disagree AND the text layer is money-shaped (`MONEYISH` after the `$` strip), OCR the same box once more with `MONEY_OCR` (tessedit_char_whitelist `0123456789$,.-`, `--psm 7`, 400 dpi). Accept only if `agree(text, ocr2)`; else `Disagreement`. Exactly one extra attempt, no loop, no config search. The corpus edit is reverted (4419.49 restored, fixtures, manifest and `benign-inv-b2-13` regenerated).
- **Consequences:** "Two independent readers must agree" holds: the re-read is still raster OCR of the cited box, it never sees the text layer, and only an exact match passes. A whitelist can only drop characters, so it can turn a letter-confusion misread into the right digits; it cannot invent a different number that equals a forged text layer unless the pixels show it. Cost: a second OCR call, only on money disagreements. Non-money boxes (ids, names) are unchanged. Misreads that survive are real false blocks, reported in the Phase 6 rate, never patched in the corpus. Guards: `tests/test_extract.py::test_money_retry_*`, `test_no_money_retry_for_a_non_money_text_layer`, `test_ocr_agreement_rate_on_benign_totals`.

## ADR-018: per-request read cache, one OCR batch, and a warm tesseract pool (latency)  — 2026-11-08 — Accepted
- **Context:** Deck target: p95 under 250 ms added. Profiling 40 benign cases (warm, pooled DB): prepare 839 ms/case, of which verification 785 ms and, inside it, the tesseract subprocess 754 ms (2.8 spawns per request at ~267 ms each). Everything else (OPA 2 ms per decision, audit append + checkpoint signature about 13 ms, SoR reads about 15 ms, commit about 19 ms) was under 60 ms. Starting tesseract.exe costs ~150 ms by itself; a read costs a few ms.
- **Options:** (a) lower dpi / drop the second reader (changes verdicts, weakens G1: rejected); (b) cache reads for the whole process (a stale or cross-document hit could authorize a write: rejected); (c) cache within one request, batch the request's boxes into one tesseract process, and keep warm single-use tesseract processes ready.
- **Decision:** (c), three parts, none of which changes what is checked.
  1. `extract.request_scope()` (a `ContextVar`, opened by `Gate.prepare` and by `verify_request`): inside it a box is read at most once. Key = (kind, sha256 of the document BYTES, page, box [, OCR config]). `amount` and `invoice.total` usually cite the same box. Failures are cached as failures. The scope ends with the request; nothing is shared across requests, threads or documents of different hash. verify still checks `sha256(blob) == doc_sha256` before any read, and prefetch only looks at documents that pass that check.
  2. `extract.prefetch`: the distinct boxes of the request are rasterized and OCRed together (`tesseract list.txt stdout --psm 7`, one process; same engine, config and image bytes, one page per image; a page-count or exit-code surprise discards the batch and every read runs singly as before). `Gate._prepare` starts it on a worker thread before its first database read so the two overlap; `verify_request` joins it.
  3. Warm pool (`OCR_POOL_SIZE`, default 0 = off, `.env.example` sets 4): `tesseract stdin stdout` initialises the engine before it waits for the image, so processes spawned ahead of time answer in about 10 ms. Each pooled process reads exactly ONE image and exits (never reused, so no state or document data crosses requests); the pool refills in the background; an empty or dead pool falls back to a cold spawn; a non-zero exit is an ExtractionError (fail closed). Children are killed at exit.
- **Consequences:** Same inputs, same verdicts: `tests/test_extract_scope.py` proves pooled and batched reads equal plain reads on the fixture boxes, one read per box per request, keys by content hash, failures stay failures, a forged document is still denied after a warm request, and the 104-total OCR agreement test passes with the pool on. Cost: up to OCR_POOL_SIZE idle tesseract processes (about 50 MB each), roughly 3 background spawns per request (CPU, not latency; under sustained load faster than the refill, requests pay a cold spawn). Not done: a persistent OCR service (the next lever if cold spawns show up in p95); lowering dpi or the whitelist (would change verdicts).

## ADR-019: durable `tool_reached` marker before the tool call (crash after the call)  — 2026-11-20 — Accepted
- **Context:** The commit runs the tool inside the SERIALIZABLE tx. If the process dies (kill, host loss) after the tool succeeded and before COMMIT, the tx rolls back with no `commits` row and no burn (burn is in-process code). A new process holding the same receipt then passes every check and calls the tool again. `tests/usp/test_exec_faults.py::test_crash_after_call_retry_must_not_double_execute[False]` reproduced a second external effect for a provider with no idempotency. A provider that dedupes on the key we pass is safe either way.
- **Options:** (a) full outbox + dispatcher (large change, changes the `EXECUTED` contract, deck rows): rejected for now; (b) write the quarantine row before the call and delete it after commit: the delete is invisible to the SERIALIZABLE snapshot and a concurrent commit on the record would see a false block; (c) a separate marker table, never deleted.
- **Decision:** (c). `tool_reached(nonce PK, record_id, created_at)` is written and committed on its own connection just before `tool.execute`. A marker with no `commits` row for its nonce counts as quarantined (`_quarantined`): prepare and commit DENY the record (AP-REP-05 / G2) until `Gate.release_quarantine`, which also clears dangling markers. After a normal commit or a burn the `commits` row exists, so the marker blocks nothing. If the marker cannot be written the tool is not called (DENY AP-ERR-11).
- **Consequences:** A crash after the call can no longer cause a second call for any provider; a crash before the call also leaves a marker (indistinguishable), so the receipt needs a human release or a fresh request. (Superseded in part by ADR-022: the marker now carries the full reservation, so a crashed attempt's amount DOES count toward the caps until reconciled.) Existing databases pick the table up through `CREATE TABLE IF NOT EXISTS`. Not an outbox: no exactly-once claim, no automatic recovery.

## ADR-020: KeyRegistry, receipts verified by their own kid  — 2026-11-20 — Accepted
- **Context:** The receipt envelope carried a `kid` but the gate verified every receipt with the active signer's key and ignored it, so rotation invalidated every unexpired receipt and the kid was decoration. Audit checkpoints already verified per kid (a kid -> key map).
- **Decision:** `signing.KeyRegistry` maps kid -> public key + status (`active`, `retired`, `revoked`). `Gate` verifies a receipt with the key of its kid; unknown or revoked kid, or a kid naming another key, fails AP-SIG-09 / G2. At most one active key; a registry that does not list the signer's kid as the active key, or is malformed, refuses to load (ConfigError). Default with no registry is unchanged: the signer's own kid only. Optional `KEY_REGISTRY_PATH` JSON. `registry.public_keys()` feeds `audit.verify` (revoked keys left out, so their checkpoints stop verifying).
- **Consequences:** Rotation no longer breaks unexpired receipts; revocation is explicit and distinct from retirement. Public keys only; the private key path is unchanged (invariant 6). No JWKS endpoint and no KMS (not built).

## ADR-021: local append-only checkpoint anchor and `audit verify --anchor [--strict]`  — 2026-11-20 — Accepted
- **Context:** The chain and signed checkpoints live in one database. Deleting the newest entries together with their checkpoints leaves a shorter valid chain (THREAT_MODEL residual); a database restored to an older state verifies too.
- **Decision:** `anchor.LocalAnchor` keeps the signed checkpoints in a hash-linked JSON-lines file (`prev` = sha256 of the previous line). Publish is idempotent and monotonic (conflicting or older = error); every line is re-verified against the trusted public keys. `audit.run_verify(..., anchor, strict)` additionally requires the database to reach the anchored seq and match its head hash (else FAILED), reports `anchored through seq A; unanchored A+1..N`, and in strict mode also fails on an unanchored tail or an empty/missing anchor. CLI: `audit anchor`, `audit verify --anchor F [--strict]` (env `AUDIT_ANCHOR_PATH`). No network call inside any transaction.
- **Consequences:** Tail-with-checkpoints deletion, rollback to an older restore and history rewrite are now detected against the anchor. NOT detected: an attacker who controls the host rewrites database and anchor file together, or drops the anchor's last lines (the shortened chain still verifies). Independence needs the file copied to WORM storage or another machine; a remote anchor is the upgrade path. Entries after the newest anchor are not externally protected and are reported, not hidden.

## ADR-022: the marker is the full logical reservation (caps, idempotency key, reconciliation)  — 2026-11-20 — Accepted
- **Context:** ADR-019's marker stored only nonce, record and time. Review found two holes it left: (1) the actor/person/refund cap sums read `commits` only, so an execution that succeeded externally and then crashed (no commits row) did not count: after a crashed $4,900 a further $250 passed the $5,000 cap; (2) the request idempotency key was not in the marker, so a new receipt on a different record with the same key executed (the failing test returned EXECUTED).
- **Decision:** `tool_reached` holds the same row a commit would (nonce, idempotency_key, request_hash, actor, on_behalf_of, vendor_id = counterparty, `numeric(18,2)` amount, record_id, created_at), written on its own connection just before the tool call. View `reservations` = `commits` UNION ALL the markers that have no commits row; the four cap sums (prepare and commit, actor+counterparty, person+counterparty, refund balance per payment) read `reservations`, exact numeric, no floats. The request idempotency key is UNIQUE on `tool_reached` (DB backstop) and the gate refuses a different nonce reusing a key held by a marker (AP-REP-05 / G2). `release_quarantine(record, reviewer, executed=False)` is the authorized reconciliation and the only way out: `executed=True` turns the reservation into a commits row (amount stays counted, key stays used), `False` deletes it (amount and key freed). Its audit entry lists each unresolved nonce and amount.
- **Audit semantics:** the crashed attempt writes NO `commit EXECUTED` entry (it was inside the rolled-back tx, and the marker's connection cannot append because the commit tx holds the audit lock). The chain therefore never claims success for an unknown outcome; it records the denied retry (AP-REP-05) and the human reconciliation (`release_quarantine`, `executed`, `unresolved`).
- **Consequences:** An unknown outcome keeps its money and its key until a human decides. Existing databases migrate with `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`; markers from the ADR-019 version have NULL amount (they still quarantine the record; SUPERSEDED by ADR-024: they do NOT count as zero, they block every cap-sensitive write until reconciled, and can be confirmed executed only with a supplied reservation). Limits: a crash before the call is indistinguishable from one after it, so it also holds its reservation until released; there is still no outbox, no automatic reconciliation and no exactly-once claim.

## ADR-023: KeyRegistry hardening and an anchor file lock  — 2026-11-20 — Accepted
- **Context:** Review of ADR-020/021 found: the same public key could be listed under two kids (a revoked or old kid could then share an active key's standing); `verify` mixed "did this key sign it" with "may it authorize"; and `LocalAnchor.publish` read, validated and appended without a lock, so two processes could fork the chain (the concurrent-publisher tests failed against it).
- **Decision:** `KeyRegistry` refuses two kids with the same public-key fingerprint (sha256 of the raw key). `signature_valid(receipt)` is cryptography only against the key of the receipt's own kid, any status; `verify(receipt)` = trusted status (active or retired) AND `signature_valid`, failing closed for revoked and unknown. `LocalAnchor.publish` and `entries` take an exclusive cross-process lock on `<file>.lock` (msvcrt on Windows, flock elsewhere, 10 s timeout then AnchorError), so the read-validate-append is atomic across processes.
- **Consequences:** Existing registries with a duplicated key now refuse to load (fix the file). A lock timeout is a publish error, not a silent skip. The `.lock` file is a sidecar and is not part of the anchor. Limits unchanged: no JWKS, no KMS, and a same-machine anchor is not WORM; flock on a network filesystem without lock support is not covered.

## ADR-024: legacy unresolved markers fail closed, never count as zero  — 2026-11-20 — Accepted
- **Context:** ADR-022 added reservation columns to `tool_reached` as nullable so rows from the ADR-019 version survive migration. Such a legacy unresolved marker has no amount, actor, counterparty or key; treating its amount as zero (what the `reservations` view does for it) would silently widen every cap.
- **Decision:** While any unresolved marker (no commits row) has a NULL reservation column, `prepare` and `commit` DENY every cap-sensitive write for every actor and record with AP-CUM-03 / G1 ("unresolved execution with an unknown amount"). `release_quarantine(record, reviewer, executed=False)` attests it did not execute (deleted, audited with `amount: null`). `release_quarantine(..., executed=True, reservation={idempotency_key, request_hash, actor, on_behalf_of, vendor_id, amount})` supplies the facts the old marker never recorded, writes them as a commit and into the audit entry (`reservation_supplied`); without a valid reservation it raises and changes nothing. The block is global, not per record, because the caps are keyed by actor and person, which a legacy row does not name.
- **Operator tooling (addendum):** `db.legacy_markers(conn)` is the single definition of an incomplete unresolved marker (also used by the gate's barrier). `python -m actionproof.reconcile check` is the explicit validation step (exit 1 if any); `scripts/apply_schema.py` and API start-up log a WARNING (boot is not refused: reconciliation needs the API); `python -m actionproof.reconcile release ...` is the audited reconciliation.

## ADR-028: policy provenance (revision bound into receipts)  — 2026-11-22 — Accepted
- **Context:** the signed receipt froze a decision but not the policy that made it; a policy reload between prepare and commit, or a human review that outlived a rule change, went unnoticed, and a past decision could not be reproduced.
- **Decision:** the revision is `policy.digest_of(modules)`: sha256 of RFC 8785 `{bundle_format, policy_schema, {file name: sha256(LF text)}}` over the `package actionproof` modules only (tests and the host's `system.authz` decide nothing and differ per deployment). The gateway reads the modules from OPA itself (`GET /v1/policies`) and the OPA version (`/v1/data/system/version`), so the revision names what is loaded, not a file on disk. `policy.decide` fetches it before every decision and returns it in `Decision`; any failure is DENY AP-POL-FAIL. The receipt gains the signed key `policy_revision`. At commit the fresh decision's revision must equal the receipt's, else AP-STALE-07 / G2 "policy revision changed since prepare; re-prepare" before anything is consumed, so a pending human review does not survive a policy change (the token stays unused). The prepare audit entry records `detail.policy = {revision, opa_version, input}` (decision rules and nonce were already there).

Unknown revision or a manifest that does not match refuses. Commit the new archive directory with every policy change.
- **Operations:** `docker/opa/authz.rego` now also allows the two read-only GETs above. Receipts from before this change lack `policy_revision` and are refused as malformed (AP-SIG-09): re-prepare any pending review across the upgrade.
- **Limits:** one extra OPA call (about 40 ms for the 140 KB module list on loopback) per prepare and per commit; the revision is read just before the decision, so a hot reload inside that window is not detected (production OPA runs without `--watch`; commit re-reads under the commit lock). There are no policy data files today; if added they must join the digest. Signed policy bundles with a separate policy-authority key are NOT implemented.
- **Tests:** tests/usp/test_policy_provenance.py (stable digest, CRLF, other packages ignored, digest equals what OPA loaded, signed revision, prepare then policy update, pending review across a change, old receipt shape, audit provenance and reconstruction, unknown revision, bad manifest).

## ADR-030: remote append-only anchor and an asynchronous publisher  — 2026-11-23 — Accepted
- **Context:** ADR-021's anchor is a file on the database host; whoever controls that host rewrites the database and the file together, and nothing watches whether checkpoints actually leave the host.
- **Decision:** `anchor.CheckpointAnchor` names the shape both anchors share (`entries`, `latest`, `publish`); `_check_signed` now also accepts a `KeyRegistry` (revoked/unknown kid fail). `anchor_remote.HttpAnchor` speaks a generic append-only HTTP protocol (`GET /checkpoints`; `PUT /checkpoints/{seq}`: 201 appended, 200 identical = idempotent no-op, 409 different head or not after the head), bearer token, no redirects, proxy env ignored; it re-verifies every listed checkpoint through the KeyRegistry and requires strictly increasing seq, and verifies before sending. `python -m actionproof.anchor_publisher once|check|run` is a separate process with its own validated env (`ANCHOR_REMOTE_URL` https or loopback http, no userinfo; `ANCHOR_REMOTE_TOKEN` >= 16 chars; `ANCHOR_STATE_PATH`; `KEY_REGISTRY_PATH`; `ANCHOR_MAX_LAG_SECONDS` 300; `ANCHOR_REMOTE_TIMEOUT_SECONDS` 5; `ANCHOR_PUBLISH_INTERVAL_SECONDS` 10); a remote URL on the database's host:port is refused. Each cycle lists the remote first, then reads the database in one READ ONLY REPEATABLE READ transaction that it commits and closes, and only then makes HTTP requests; it never takes the audit lock, never writes to the database and holds no private key. It publishes every checkpoint above the remote head in seq order and stops at the first failure, so recovery resumes there. Detected (exit 1): conflicting head vs the local chain, gap, remote behind the last verified head (state file), database shorter than the remote, broken local chain (`check` runs `audit.verify`), lag; an unreachable remote is WARN (exit 0) for `once`/`run` within the lag budget and exit 1 for `check`. Exit 2 = config. Output never holds the token or the DSN.
- **Consequences:** A host owner can no longer rewrite the chain consistently with checkpoints already held remotely without `check` failing. Limits: tested only against an in-process STUB; UNVERIFIED against a real provider and not WORM unless the provider's retention lock is enforced and verified by the operator; checkpoints newer than the last publish (up to the lag budget) are not externally protected; deleting the state file removes remote-rollback detection (keep it on the monitoring host); a remote that drops its newest entries before the monitor ever saw them is indistinguishable from slow publication (reported as lag/unpublished, not rollback); one HTTP PUT per checkpoint and the snapshot reads every checkpoint (ponytail). `.env.example` does not list the ANCHOR_* variables yet (file not owned by this phase).
- **Tests:** tests/usp/test_anchor_remote.py (16).

## ADR-029: execution journal and truthful audit semantics  — 2026-11-23 — Accepted
- **Context:** the `commit` EXECUTED audit entry was written inside the commit tx BEFORE `tool.execute`. It only became visible if the tx committed, but a process that died after the downstream effect left the chain with no success entry and the outcome visible only as an unresolved `tool_reached` row. There was no durable, tamper-evident record of what was dispatched and what came back.
- **Decision:** a new append-only table `execution_journal` (journal.py) with its own hash chain (entry_hash = sha256(RFC 8785 of every other column)), seq under a journal-only advisory lock, triggers as on the audit tables, and `verify`. execution_id = "ex-" + sha256("actionproof.execution:" + nonce)[:32]. Events (exact): RESERVATION_CREATED, DISPATCH_STARTED, EXECUTION_CONFIRMED, EXECUTION_FAILED, EXECUTION_UNKNOWN, RECONCILIATION_STARTED, RECONCILIATION_COMPLETED; each carries the full reference (nonce, request_hash, idempotency_key, record_id, actor, on_behalf_of, vendor_id, amount as numeric(18,2) / 2dp string). Partial unique indexes: one reservation, one dispatch and at most one outcome per execution.
- **Commit path:** the audit EXECUTED entry is rehearsed in a savepoint that is always rolled back (an audit store that cannot take it stops the tool: DENY AP-ERR-11, nothing reserved, as before). The marker connection then writes `tool_reached` + RESERVATION_CREATED + DISPATCH_STARTED in one tx, committed before the call. Tool returns -> EXECUTION_CONFIRMED on its own connection, then the EXECUTED audit entry (with `execution_id` and `journal {seq, entry_hash}` of the CONFIRMED event), then the main commit. Tool raises -> burn + quarantine as before, then EXECUTION_FAILED only for `journal.DefiniteFailure` (an adapter's explicit "not applied"), else EXECUTION_UNKNOWN. Any other failure after dispatch (serialization, STALE after the call, a failed CONFIRMED write) burns and journals the attempt's outcome unless one is already journaled (CONFIRMED is retried, never downgraded to UNKNOWN). A crash journals nothing more: DISPATCH_STARTED with no outcome reads UNKNOWN.
- **Lock order:** audit -> journal. Journal writes use their own short connections and never take the audit lock, so the commit and release txs (which hold it) may write the journal; nothing holding the journal lock waits for the audit lock. No cross-connection audit append. `release_quarantine` now takes the audit lock first (common lock-order rule).
- **Reconciliation:** `release_quarantine` validates everything, journals RECONCILIATION_STARTED for each journaled execution it resolves (the audit entry lists their seq/hash), commits the release with its audit entry, then journals RECONCILIATION_COMPLETED {resolution CONFIRMED|FAILED, resolver, audit_seq}. New `evidence=` argument: downstream evidence {source, idempotency_key, status APPLIED|NOT_APPLIED, amount, counterparty} must match the one journaled execution on the record exactly or nothing changes (ValueError); resolver = {kind: evidence, source, operator}. A journaled CONFIRMED execution cannot be released as not executed (human or evidence). Nothing is time-based; an UNKNOWN is never redispatched. CLI: `python -m actionproof.reconcile journal verify|list [--all]|resolve --execution ID --reviewer LOGIN (--executed|--not-executed|--evidence JSON)`.
- **Migration:** CREATE TABLE / INDEX IF NOT EXISTS, CREATE OR REPLACE TRIGGER: idempotent on existing databases. `tool_reached`, `reservations` and the gate's checks are unchanged (the journal is additive and references the same row). Unresolved markers written before this table have no events: nothing is backfilled; they are reconciled with `reconcile release` exactly as before and the release gets no journal events.
- **Limits:** no exactly-once claim for arbitrary downstreams. A definite failure still burns and quarantines (conservative accounting; ponytail: release automatically once adapters have a verified failure contract). No adapter raises DefiniteFailure yet. Evidence authenticity is the operator's responsibility (ponytail: signed adapter lookup). For the in-DB mock tools, "CONFIRMED" means the adapter returned; their effect still rolls back with the main tx. If the COMPLETED write is lost after the release commits, the execution reads RECONCILING (the audit entry is the record). The journal is not covered by signed checkpoints or the external anchor (only the hash chain).
- **Tests:** tests/usp/test_exec_journal.py.

## ADR-033: signed policy revisions with a separate policy-authority key  — 2026-11-23 — Accepted
- **Context:** ADR-028 binds the revision OPA loaded into receipts: it proves WHICH policy decided, not that an authorised owner published it. Anyone able to edit `policy/` or PUT a module into OPA changes the revision silently and every receipt records it honestly.

## ADR-034: signed checkpoints and anchoring for the execution journal  — 2026-11-23 — Accepted
- **Context:** ADR-029's execution journal is append-only and hash-chained, but nothing signs its head and nothing copies it off the host. Anyone with database write access (owner, superuser, a restored older dump) can drop the newest events, for example the DISPATCH_STARTED / EXECUTION_CONFIRMED that show money moved, or rebuild a consistent shorter chain; the chain still links and `journal verify` said OK.
- **Decision:** a new append-only table `execution_journal_checkpoints {seq, head_hash, ts, sig, kid}` (same trigger function as the audit tables; `CREATE TABLE IF NOT EXISTS`, schema stays idempotent; added to `db.AUDIT_TABLES` for the test reset). `journal.checkpoint(conn, signer)` signs `{seq, head_hash, ts}` with the gate's checkpoint signer exactly like `audit.checkpoint`, under the journal's own advisory lock and nothing else (the journal rule "never wait on the audit lock" holds; a test holds the audit lock while it runs), idempotent for an unchanged head, and refuses (JournalFailure) to sign when the newest checkpoint is beyond or differs from the head. `journal.verify(conn, keys=None)` additionally checks every checkpoint with the same trust rules as `audit.verify` (one key; a kid map, unknown kid fails; or a KeyRegistry, revoked fails too), head_hash against the chain, and a checkpoint beyond the head (truncated tail); checkpoints present but no key = failure (fail closed); called without keys on a journal with no checkpoints it behaves as before. `journal.anchor_report` applies audit's anchor policy to the journal (database older than / diverging from the anchor = fail; unanchored tail fails only with `--strict`). Anchoring reuses the unchanged `LocalAnchor` / `HttpAnchor` classes as a separate stream: a distinct file (the CLI refuses `AUDIT_ANCHOR_PATH`) and the remote path `{ANCHOR_REMOTE_URL}/journal/checkpoints/{seq}`. `anchor_publisher` runs one per-stream cycle for audit, then journal (independent; worst exit code; lines `anchor-remote:` / `anchor-remote[journal]:`; state `ANCHOR_STATE_PATH` and `ANCHOR_STATE_PATH.journal`), keeping list-remote, one closed read-only snapshot, compare, then HTTP. CLI: `python -m actionproof.reconcile journal checkpoint [--anchor F]` (verifies the chain first, signs, commits, closes, then appends to the anchor) and `journal verify [--anchor F] [--strict]`; keys from `KEY_REGISTRY_PATH`, else the gate's own signer (as `server.build_app`); exit 0 OK, 1 failed, 2 config.
- **Consequences / limits:** the Gate does not checkpoint the journal (gate.py was out of scope): events after the last scheduled `journal checkpoint` are unpinned, exactly like `AUDIT_CHECKPOINT_EVERY>1`; schedule it (RUNBOOK). The signed payload has no stream tag (anchor's `_check_signed` requires exactly `{seq, head_hash, ts}`), so the two streams are kept apart by path and file, and a cross-stream copy is caught only because its head_hash cannot match the other chain (tested). Same gate key as receipts and audit: a leaked key can sign a rewritten journal, but not one consistent with checkpoints already anchored. `checkpoint` and the CLI's prior `verify` are two statements: an event appended between them is signed without having been re-verified in that run (the next verify checks it). `verify` holds every entry hash in memory (ponytail, as audit). Remote adapter tested only against the in-process STUB: UNVERIFIED against a real provider; no WORM or tamper-proof claim. `cycle()` called without `journal_remote` builds a new client per call (main and run build it once).
- **Tests:** tests/usp/test_journal_checkpoints.py (17); tests/usp/test_anchor_remote.py stub extended to serve the second stream (no assertion changed).

## ADR-035: definite-failure evidence and an outbox with automatic reconciliation  — 2026-11-23 — Accepted
- **Context:** ADR-029 journals FAILED whenever an adapter raises `journal.DefiniteFailure`, on the adapter's word alone, and resolves an UNKNOWN execution only when a human runs `reconcile` (the evidence path trusted whatever JSON the operator pasted). Nothing re-asked the provider, and a forged or buggy "declined" was indistinguishable from a real one.
- **Decision:** (1) `evidence.py` defines the adapter statement `{kind: "actionproof.adapter-evidence.v1", op: execute|lookup, idempotency_key, status: APPLIED|NOT_APPLIED|UNKNOWN, amount (2dp string), counterparty, reason (typed code `^[A-Z][A-Z0-9_]{1,63}$`, required for NOT_APPLIED), provider_ref (required for APPLIED), response_digest (sha256 of the provider response), ts, window_closes_at}` signed with `signing.Signer` (RFC 8785, floats refused). It is believed only through `KeyRegistry.verify` (active/retired kid; unknown/revoked fail) of the gate's adapter registry and only when it names this execution exactly; `verified()` never raises. (2) Trust: `Gate(..., adapter_keys=KeyRegistry)`, default from `ADAPTER_EVIDENCE_KEYS` (loaded with the strict policy-authority loader: public keys + status only), validated at config load; an adapter key equal to a receipt key is refused at Gate construction; unset = no adapter is trusted. The repo's mock adapter signs with a test key in `tests/fixtures/adapter-evidence.seed` only. (3) Dispatch path (gate.py post-dispatch only): `evidence.dispatch_failure` -> EXECUTION_FAILED with `detail.evidence {kid, digest, reason}` for a verified execute NOT_APPLIED, else EXECUTION_UNKNOWN (`evidence: "unverified"` for a rejected DefiniteFailure; other errors keep `{error}`). ADR-010 accounting is unchanged for both. (4) Outbox: table `execution_outbox` and `outbox.py`, run by `python -m actionproof.reconcile auto --once|--run [--min-age 60] [--interval 10]` (exit 2 without adapter trust). Enqueue from the journal (DISPATCH_STARTED older than min-age; PENDING if UNKNOWN, else DONE), claim with `FOR UPDATE SKIP LOCKED` + 30 s lease (committed), `lookup(idempotency_key)` outside any transaction, `evidence.lookup_outcome`: APPLIED -> CONFIRMED; NOT_APPLIED with `0 < window_closes_at <= ts` and `window_closes_at <= now` (statement not more than 300 s ahead of the worker clock) -> DEFINITE_FAILURE; anything else AMBIGUOUS (backoff 5 s doubling, cap 300 s). A conclusive result is applied only after re-fencing the lease, through `Gate.release_quarantine(evidence={source: "adapter.lookup:<kid>:<digest>", ...})`, i.e. the existing audited, journaled path and its existing accounting (crash marker: APPLIED -> commits row, NOT_APPLIED -> marker deleted; burned execution: quarantine lifted, burn kept). The worker never calls `execute`.
- **Consequences / limits:** no exactly-once claim for an external system: a provider (key holder) that signs a false NOT_APPLIED frees a reservation under the existing evidence semantics, and a provider without lookup-by-idempotency-key is never auto-resolved (stays UNKNOWN, counted, surfaced as stuck). The registry is shared by all adapters (a statement is bound to the execution, not to a tool). `--min-age` is a heuristic: a gate dispatch slower than it is enqueued while in flight; it is safe (release_quarantine blocks on the audit lock the commit holds, then refuses, and the row is marked ALREADY_RESOLVED) but not proven by a test. The outbox is not driven by the gate (the gate still dispatches synchronously in commit; "needs dispatch" rows are not built) and `execution_outbox` is not in `db.reset` (db.py not owned; the test truncates it). `.env.example` does not list `ADAPTER_EVIDENCE_KEYS` (not owned). Only `MockPayments` has `lookup`/signing; `MockRefunds` and `ProxyAdapter` have neither (their UNKNOWNs stay for humans). The enqueue scan reads the journal status of new dispatches only (rows are inserted DONE for the rest).
- **Tests:** tests/usp/test_adapter_evidence.py (25), tests/usp/test_outbox.py (19); tests/usp/test_exec_journal.py::test_definite_failure_is_failed_and_still_single_use changed to sign its evidence (a bare DefiniteFailure is now UNKNOWN by design).

## ADR-036: commit lane stays global; the audit lock is the serial section  — 2026-11-23 — Accepted
- **Context:** Gate.commit takes `LOCK TABLE commits IN SHARE ROW EXCLUSIVE MODE` (one global lane) and then `audit.lock` (EXCLUSIVE on audit_log, needed so seq = head + 1 and the hash chain stay gap-free), both before the SERIALIZABLE snapshot. The ponytail note named a per-(actor, vendor) lock as the upgrade path. That only pays off if the lane, not the audit lock, is what serialises commits.
- **Measurement (docs/PERFORMANCE.md "Commit lane"):** `scripts/bench_commit_lanes.py`, real Postgres + OPA, unchanged gate code. Throughput is 11-14 commits/s at 1, 4, 8 and 16 workers, on one (actor, vendor) pair and on distinct pairs; p50 grows linearly with workers (74 ms -> ~1.2 s). The audit lock is held ~72-80 ms of a ~78 ms commit (taken at tx start, held through the OPA re-check, marker/journal writes, tool call, EXECUTED entry and commit). A bench-only variant with NO lane at all (the upper bound of any lane replacement) gives the same throughput within the rep spread; the wait just moves from the lane to the audit lock. About 40-47 ms per commit is Python thread CPU.
- **Decision:** locking unchanged. Per-(actor, counterparty) advisory locks are rejected for now: they cannot add parallelism while every commit holds the audit lock for its whole length, and they would add lock-order and cross-vendor / per-person cap reasoning for no gain.
- **Future step (not done):** audit sequencing. Allocate the audit position from a sequence (or write per-commit staging rows) and link prev_hash/entry_hash in a single chain-writer after commit, so the commit tx no longer holds an EXCLUSIVE audit lock. Only then re-evaluate per-(actor, counterparty) locks, keeping "audit first" lock order, the actor-across-vendors and per-person AP-CUM-03 totals, and G2 (DB uniqueness on nonce/idempotency key, review-token single use). Re-run the bench before and after.
- **Limits:** one Windows laptop, client threads in one Python process (GIL), mock adapter (no network latency in the tool call), wall-clock attribution rather than pg_stat_activity wait events.
